# Cross-client reference lab (BT-02)

Status: **opt-in harness, one direction verified, two rows explicitly
unsupported.** Nothing here runs in normal CI: every entry point skips unless
`PROVENANCE_TEST_BITTORRENT_CROSSCLIENT=1` is set, and then skips again if the
pinned client image is not already on the machine. The lab never pulls an image.

The point of the lab is to stop treating "our own library seeded it, our own
library fetched it" as interoperability. It puts a real, independently
implemented BitTorrent peer on the other end of a socket and measures what
happens.

## The client under test

| Item | Value |
|------|-------|
| Image | `lscr.io/linuxserver/qbittorrent@sha256:05c1454f…` (never `latest`) |
| Client | qBittorrent v5.3.0 |
| Peer-wire library | libtorrent 2.1.2.0 |
| Image build date | 2026-11-01 |

Override with `PROVENANCE_TEST_BITTORRENT_CROSSCLIENT_IMAGE`; the image must be
present locally, because this host cannot pull from a registry.

## Isolation

- A dedicated bridge network `provenance-bt-lab` created with
  `com.docker.network.bridge.enable_ip_masquerade=false`, so the container has no
  route off the host. Measured: an outbound TCP connection from inside the
  container times out, while host→container traffic on the bridge works
  (`--internal` was rejected as an alternative because it also blocks published
  ports).
- `--dns 127.0.0.1`, so the container's embedded resolver has nothing to forward
  to.
- The container runs as the invoking user, from a bind-mounted throwaway
  `/config` and `/data`.
- qBittorrent is configured with DHT, PEX, LSD, uTP, queueing and ratio limits
  off, UPnP/NAT-PMP off, a fixed peer port, and no trackers anywhere. Torrents
  are introduced by hand: the lab never announces to anything.
- In the one direction that needs it, the container shares the host's network
  namespace (Provenance's `direct` profile binds its listener to loopback by
  design), and the WebUI plus the peer listener are then pinned to `127.0.0.1`
  through the config.

## Why row 1 needed a product change

The first attempts failed about half the time, and the failure was not where it
looked. The trace showed `peers active=0 permanent` for the whole deadline, i.e.
the library had never kept a peer. A raw 68-byte handshake sent by the test to
the container's listen port got `EOF` on the first attempt and a valid reply one
second later: **qBittorrent reports a torrent complete (`progress=1`,
`stalledUP`) before libtorrent will accept peer connections for it.**

The pinned library dials an explicit peer once, drops it when the handshake
fails, and never retries that address — so one early dial stalled the entire
fetch until the deadline. `waitForInfo` and `waitComplete` now re-offer the
configured peers every 5 s while no peer is connected
(`peerRetryInterval`), which is covered by two deterministic tests in
`peer_retry_test.go`:

- `TestExplicitPeerIsReofferedAfterAFailedHandshake` — a TCP proxy closes the
  first two connections (both of the library's handshake flavours); the fetch
  still completes, and it can only complete after the retry interval.
- `TestHealthyPeerIsNotRedialled` — a healthy fetch dials the peer exactly once,
  so the retry never churns a working connection.

After the change, row 1 went from 1/3 to 3/3.

## What this lab does not prove

- **No v2-only or hybrid peer-wire interop.** Rows 4–5 above.
- **No encrypted peer-wire interop.** Row 6.
- **No cross-client leeching test.** Direction 3 is blocked, so "we serve bytes
  another client accepts" is still unproven.
- **No real network path.** Everything is loopback or a host-local bridge; no
  NAT, no packet loss, no actual swarm.
- **Isolation is a docker bridge, not a firewall.** The container has no route
  off the host and no resolver, but it shares the host kernel; the lab asserts
  configuration (no trackers, no DHT/PEX/LSD) rather than capturing packets.

## Running it

```bash
PROVENANCE_TEST_BITTORRENT_CROSSCLIENT=1 \
  go test ./internal/transfer/bittorrent/ -run 'TestCrossClient' -count=1 -v
```

It needs a reachable docker daemon and the pinned image locally. A run takes
about 10 seconds per container start; the lab creates and removes its own
network, containers and temp directories.
